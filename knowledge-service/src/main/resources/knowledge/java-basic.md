## HashMap 的扩容机制

HashMap 在 JDK8 中默认初始容量 16，负载因子 0.75。当元素数量超过 `容量 × 负载因子` 时触发扩容，容量翻倍。

扩容的关键在于**元素不需要重新计算 hash**：因为容量是 2 的幂，元素在新表中的位置只取决于 `hash & (oldCap - 1)` 和 `hash & oldCap`。JDK8 用高低位链表拆分：按位与结果为 0 的元素留在原索引，结果为 1 的元素移动到 `原索引 + 原容量`。

JDK7 使用头插法，扩容时链表顺序反转，多线程并发扩容可能形成环形链表导致 CPU 100%；JDK8 改为尾插法修复了这个问题。

负载因子 0.75 是空间与时间的折中：太低浪费内存，太高哈希冲突率上升。

## HashMap 链表转红黑树的阈值

JDK8 中链表长度达到 8 且数组容量不小于 64 时，链表转为红黑树；元素减少到 6 时退化为链表。

阈值 8 来自泊松分布：在负载因子 0.75 的假设下，单个桶内元素数达到 8 的概率约为 0.00000006，正常情况下几乎不会树化，树化只是极端哈希冲突下的兜底，把查询从 O(n) 降到 O(log n)。

退化阈值取 6 而不是 7，是为了留出缓冲区，避免元素在 7 和 8 之间反复增删导致频繁树化与退化。

如果数组容量小于 64，即使链表长度超过 8 也优先扩容而不是树化，因为小数组扩容的收益更高。

## String 为什么设计成不可变

String 被 final 修饰，内部字符数组（JDK9 起为 byte[]）也是 final 且不对外暴露，因此不可变。

四个理由：

1. **字符串常量池可以安全共享**：相同字面量复用同一个对象，节省内存。
2. **hash 值可以缓存**：String 缓存了 hashCode，作为 HashMap 的 key 时性能稳定。
3. **线程安全**：不可变对象天然线程安全，无需加锁。
4. **安全性**：类加载的类名、数据库连接串、文件路径等参数不会在中途被篡改。

代价是每次拼接都会产生新对象，所以循环内拼接必须用 StringBuilder，而不是 `+`。

## StringBuilder 与 StringBuffer 的区别

两者都是可变字符序列，区别在同步策略：

- StringBuffer 的方法大多用 synchronized 修饰，线程安全但有锁开销。
- StringBuilder 不加锁，单线程下性能更好。

选择原则：单线程或方法内部局部变量用 StringBuilder；只有真正跨线程共享同一个缓冲区时才需要 StringBuffer，而这种场景在实践中极少。

JDK9 之后字符串拼接的 `+` 在编译期会被 javac 优化为 invokedynamic 调用 StringConcatFactory，不再等价于 StringBuilder 链式 append，但循环体内的拼接仍建议显式使用 StringBuilder。

## equals 与 hashCode 的约定

重写 equals 必须重写 hashCode，否则会破坏哈希容器的行为。

约定：
1. 两个对象 equals 相等，hashCode 必须相等。
2. hashCode 相等，equals 不一定相等（哈希冲突）。
3. equals 不相等，hashCode 可以相等。

违反第一条会导致 HashMap 中"存进去却查不到"：对象用默认的 Object.hashCode（内存地址相关）算出的桶位置，与用逻辑相等判断的桶位置不一致。

实现要点：hashCode 用参与 equals 判断的字段计算；equals 先判引用相等、再判类型、再逐字段比较。

## 接口与抽象类的选择

抽象类是"是不是"的关系，接口是"能不能"的关系。

- 抽象类可以有构造器、成员变量、方法实现，单继承。
- 接口在 JDK8 之后可以有 default 方法和 static 方法，JDK9 之后可以有 private 方法，但字段只能是 public static final，多实现。

选择原则：需要复用代码骨架（模板方法模式）用抽象类；只是定义能力契约用接口。现代 Java 更倾向于"接口 + default 方法"来替代部分抽象类，因为不受单继承限制。

## 泛型擦除

Java 的泛型是编译期特性，编译后类型参数被擦除为它的上界（无界则为 Object），因此运行期拿不到真实类型参数。

带来的限制：
- 不能 `new T()`，不能 `new T[]`。
- 不能对泛型类型做 instanceof 判断（除非是无界通配符）。
- 静态成员不能使用类的类型参数。

擦除是为了兼容 JDK5 之前的字节码。需要在运行期获取类型信息时，通常传入 `Class<T>` 或使用 TypeToken 保留泛型签名。

## 反射的代价与使用场景

反射在运行期解析类结构，绕过编译期检查，因此：
- 性能低于直接调用（方法查找与访问检查有开销，JDK 内部有 inflation 机制缓解）。
- 破坏封装，可以访问私有成员。
- 编译期无法发现错误，重构时不安全。

典型场景：框架的依赖注入、ORM 映射、JSON 序列化、动态代理。业务代码应避免滥用反射，优先用接口和组合。

## Java 的四种引用

- **强引用**：普通的 `new`，只要可达就不回收，是 OOM 的主要来源。
- **软引用 SoftReference**：内存不足时回收，适合做缓存。
- **弱引用 WeakReference**：只要发生 GC 就回收，ThreadLocal 的 Entry 用弱引用指向 key。
- **虚引用 PhantomReference**：无法通过它获取对象，只在对象被回收时收到通知，用于管理堆外内存（如 DirectByteBuffer 的 Cleaner）。

## final、finally、finalize 的区别

- `final` 是修饰符：修饰类不可继承，修饰方法不可重写，修饰变量不可重新赋值（引用不可变，对象内容可变）。
- `finally` 是异常处理的收尾块，无论是否抛异常都会执行（System.exit 除外），常用于释放资源。
- `finalize` 是 Object 的方法，GC 前调用，执行时机不确定、可能不被调用、拖慢回收，JDK9 起标记为废弃，应改用 try-with-resources 或 Cleaner。
