## 联合索引与最左前缀原则

联合索引 `(a, b, c)` 的 B+ 树先按 a 排序，a 相同再按 b，b 相同再按 c。因此只有从最左列开始、连续匹配的条件才能用上索引。

**能命中**：`WHERE a=?`、`WHERE a=? AND b=?`、`WHERE a=? AND b=? AND c=?`、`WHERE a=? AND c=?`（a 用于索引，c 无法用于定位但可用于覆盖索引）。

**不能命中**：`WHERE b=?`、`WHERE b=? AND c=?`（跳过最左列）。

范围查询会让其后的列无法继续用于索引定位：`WHERE a>? AND b=?` 中 b 只能做索引条件下推（ICP）过滤，不能缩小扫描范围。

## 索引失效的常见场景

1. **跳过最左列**：联合索引 `(a,b)` 只查 b。
2. **对索引列做函数或运算**：`WHERE YEAR(created_at)=2026`、`WHERE id+1=10`。
3. **隐式类型转换**：`varchar` 列用数字比较 `WHERE phone=13800138000`，等价于对列做 CAST，索引失效。
4. **LIKE 以 % 开头**：`LIKE '%abc'` 无法利用 B+ 树的有序性。
5. **OR 连接非索引列**：`WHERE a=? OR d=?`，d 无索引则整体退化为全表扫描。
6. **使用 `!=` 或 `NOT IN`** 时优化器可能放弃索引（取决于选择性）。
7. **索引列参与排序方向不一致**：`ORDER BY a ASC, b DESC` 在 MySQL 8.0 之前无法用索引排序。

## 为什么 InnoDB 用 B+ 树而不是 B 树或哈希

- **相比 B 树**：B+ 树非叶子节点只存键不存数据，同样大小的页能容纳更多键，树更矮（通常 3 层可存千万级数据），磁盘 IO 次数更少；且叶子节点用双向链表相连，范围查询只需顺序遍历叶子，B 树需要中序遍历回溯。
- **相比哈希索引**：哈希只支持等值查询，不支持范围查询和排序，且哈希冲突严重时退化。InnoDB 的自适应哈希索引（AHI）只是在内存中为热点页加速等值查询，不作为主索引结构。

## 聚簇索引与二级索引

InnoDB 的主键索引是**聚簇索引**：叶子节点直接存储整行数据，数据即索引。

二级索引（辅助索引）的叶子节点存储的是**主键值**，不是行指针。因此通过二级索引查非索引列时需要**回表**：先查二级索引拿到主键，再回主键索引取整行，两次 B+ 树查找。

**覆盖索引**可以避免回表：查询的所有列都在索引里时，直接从二级索引返回。例如 `SELECT id, name FROM user WHERE name=?` 若存在 `(name)` 索引且 id 是主键，可直接返回。

## MVCC 的实现原理

MVCC（多版本并发控制）让读写互不阻塞，实现依赖三部分：

1. **隐藏字段**：每行有 `DB_TRX_ID`（最后修改该行的事务 ID）和 `DB_ROLL_PTR`（指向 undo log 中的旧版本）。
2. **undo log 版本链**：每次修改把旧值写入 undo log，通过回滚指针串成链。
3. **ReadView**：一致性读时生成，包含当前活跃事务 ID 列表 `m_ids`、最小活跃事务 ID、下一个待分配事务 ID。

可见性判断：沿版本链找到第一个可见版本。若 `DB_TRX_ID` 小于最小活跃 ID 则可见；若在活跃列表中则不可见，继续沿链回溯。

**RC 与 RR 的差别**：RC 每条 SELECT 生成一次 ReadView，所以能看到别人已提交的新数据；RR 只在事务第一次 SELECT 时生成，后续复用，因此可重复读。

## 事务隔离级别与幻读

SQL 标准四种隔离级别：

| 级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| 读未提交 | 可能 | 可能 | 可能 |
| 读已提交 | 不可能 | 可能 | 可能 |
| 可重复读 | 不可能 | 不可能 | InnoDB 下基本不可能 |
| 串行化 | 不可能 | 不可能 | 不可能 |

MySQL 默认 RR。InnoDB 在 RR 下用 **Next-Key Lock**（记录锁 + 间隙锁）解决幻读：范围查询会锁住区间及间隙，阻止其它事务插入。注意快照读（普通 SELECT）靠 MVCC 解决幻读，当前读（`SELECT ... FOR UPDATE`、UPDATE、DELETE）靠 Next-Key Lock。

## 慢查询的排查步骤

1. **开启慢查询日志**：`slow_query_log=ON`，`long_query_time=1`。
2. **用 `EXPLAIN` 看执行计划**：关注 `type`（ALL 全表 < index < range < ref < eq_ref < const）、`key`（实际使用的索引）、`rows`（预估扫描行数）、`Extra`（Using filesort / Using temporary 是危险信号）。
3. **用 `EXPLAIN ANALYZE`（8.0.18+）** 看实际耗时。
4. **优化方向**：加合适索引、改写 SQL 避免函数运算、减少回表（覆盖索引）、分页优化（延迟关联）、拆分大事务。
5. **用 `SHOW PROFILE` 或 performance_schema** 定位耗时在解析、执行还是发送阶段。

## 为什么推荐自增主键

InnoDB 使用聚簇索引，数据按主键顺序物理存储。自增主键保证插入总在 B+ 树末尾追加，页分裂少、顺序写快。

UUID 随机分布，插入位置随机，会导致频繁页分裂、随机 IO，且 36 字节比 BIGINT 的 8 字节更大，二级索引也要存主键，索引体积膨胀。

分布式场景可用**雪花 ID**：64 位，由时间戳 + 机器 ID + 序列号组成，趋势递增，兼顾唯一性与插入性能。代价是需要处理时钟回拨。
