## JVM 运行时内存区域划分

**线程私有**：
- 程序计数器：记录当前字节码行号，是唯一不会抛 OutOfMemoryError 的区域。
- 虚拟机栈：每个方法调用对应一个栈帧，存放局部变量表、操作数栈、动态链接、返回地址。栈深度超限抛 StackOverflowError。
- 本地方法栈：为 native 方法服务。

**线程共享**：
- 堆：对象实例的主要分配区域，GC 的主战场，分新生代（Eden + 两个 Survivor）和老年代。
- 方法区：JDK8 起由永久代改为元空间 Metaspace，使用本地内存，存放类元信息、常量、静态变量。

## 对象进入老年代的四种情况

1. **大对象直接进老年代**：超过 `-XX:PretenureSizeThreshold` 的对象直接分配在老年代，避免在 Eden 与 Survivor 之间反复复制。
2. **长期存活对象晋升**：每熬过一次 Minor GC 年龄加 1，达到 `-XX:MaxTenuringThreshold`（默认 15）晋升老年代。
3. **动态年龄判定**：Survivor 中所有同龄对象大小总和超过 Survivor 空间的一半，则年龄大于等于该年龄的对象直接晋升，不必等到阈值。
4. **分配担保**：Minor GC 后 Survivor 放不下存活对象，通过老年代的分配担保机制直接进入老年代。

## 垃圾回收算法与分代收集

**基础算法**：
- 标记-清除：标记存活对象后清除垃圾，产生内存碎片。
- 复制算法：把存活对象复制到另一半空间，无碎片但浪费空间，适合存活率低的新生代。
- 标记-整理：标记后把存活对象向一端移动，无碎片但移动成本高，适合老年代。

**分代收集**：新生代存活率低用复制算法（Eden : Survivor = 8 : 1 : 1），老年代存活率高用标记-整理或标记-清除。

## 如何判断对象已死

主流 JVM 使用**可达性分析**，而不是引用计数（引用计数无法解决循环引用）。

从一系列 GC Roots 出发向下搜索，不可达的对象判定为可回收。GC Roots 包括：
- 虚拟机栈中局部变量表引用的对象
- 方法区中静态属性引用的对象
- 方法区中常量引用的对象
- 本地方法栈中 JNI 引用的对象
- 活跃线程、同步锁持有的对象

对象被判定不可达后还要经历两次标记，期间若在 finalize 中重新建立引用可自救，但 finalize 已废弃。

## 类加载过程与双亲委派

类加载五个阶段：加载 → 验证 → 准备 → 解析 → 初始化。

**双亲委派**：类加载器收到加载请求时先委派给父加载器，父加载器无法完成才自己加载。

三层结构：Bootstrap（加载 JDK 核心类）→ Extension/Platform → Application（加载 classpath）。

**作用**：
1. 避免类被重复加载。
2. 保证核心类不被篡改：即使自定义一个 `java.lang.String`，也会因父加载器已加载而被拒绝。

**打破双亲委派的场景**：SPI 机制（JDBC 的 DriverManager 用线程上下文类加载器）、Tomcat 的 WebApp 隔离、OSGi。

## JVM 常用调优参数

- `-Xms` / `-Xmx`：堆初始大小与最大大小，生产建议设为相同值，避免运行时反复扩容。
- `-Xmn`：新生代大小。
- `-XX:MetaspaceSize` / `-XX:MaxMetaspaceSize`：元空间初始与上限。
- `-XX:+UseG1GC`：启用 G1 收集器（JDK9 起为默认）。
- `-XX:MaxGCPauseMillis`：G1 的目标停顿时间。
- `-Xss`：单线程栈大小。
- `-XX:+HeapDumpOnOutOfMemoryError`：OOM 时导出堆快照，是线上排查的必备参数。

## 内存泄漏的常见原因

Java 的内存泄漏指对象已不再使用但仍被引用，GC 无法回收：

1. **静态集合持有对象**：static Map 不断 put 却不 remove。
2. **ThreadLocal 未 remove**：线程池中线程长期存活，Entry 的 value 一直被引用。
3. **监听器未注销**：注册后忘记反注册。
4. **连接/流未关闭**：数据库连接、文件流、网络流。
5. **缓存无上限**：没有淘汰策略的本地缓存。
6. **内部类持有外部类引用**：非静态内部类隐式持有外部实例。

排查手段：jmap 导出堆快照，用 MAT 或 JProfiler 分析支配树，找增长最快的对象及其 GC Root 引用链。
