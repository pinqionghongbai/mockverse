## Redis 的五种基本数据类型与应用场景

- **String**：缓存对象、计数器（INCR）、分布式锁（SET NX EX）、会话。
- **Hash**：存储对象的多个字段，可单独更新某个字段，适合购物车、用户信息。
- **List**：双向链表，支持 LPUSH/RPOP，适合消息队列（简易）、最新列表。
- **Set**：无序去重集合，支持交并差，适合标签、共同好友、抽奖去重。
- **ZSet**：带分数的有序集合，底层跳表 + 哈希表，适合排行榜、延时队列（分数为时间戳）。

扩展类型：Bitmap（签到、布隆过滤器底层）、HyperLogLog（UV 统计，误差 0.81%）、GEO（地理位置）、Stream（消息队列）。

## Redis 的单线程模型与为什么快

Redis 6.0 之前命令处理是**单线程**的（网络 IO 也是单线程）；6.0 起网络 IO 多线程，但命令执行仍是单线程。

快的三个原因：
1. **纯内存操作**，避免磁盘 IO。
2. **单线程避免了锁竞争和上下文切换**。
3. **IO 多路复用**（epoll）让单线程能处理大量并发连接。

单线程的代价：一个慢命令（如 `KEYS *`、大 key 的 `DEL`）会阻塞所有请求。所以生产禁止使用 `KEYS`，要用 `SCAN` 渐进遍历；删除大 key 用 `UNLINK` 异步释放。

## 过期删除策略与内存淘汰策略

这是两个不同层次的问题。

**过期删除**（解决"key 到期了怎么删"）：
- 惰性删除：访问时才检查是否过期。
- 定期删除：每 100ms 随机抽取一批设置了过期时间的 key 检查。

**内存淘汰**（解决"内存满了删谁"），`maxmemory-policy` 八种：
- `noeviction`：不淘汰，写入报错（默认）。
- `allkeys-lru` / `allkeys-lfu`：所有 key 中按最近最少使用 / 最少使用频率淘汰。
- `volatile-lru` / `volatile-lfu` / `volatile-ttl` / `volatile-random`：只在设置了过期时间的 key 中淘汰。
- `allkeys-random`：随机淘汰。

做缓存一般用 `allkeys-lru`；若部分 key 必须常驻，用 `volatile-lru` 并只给可淘汰的 key 设过期时间。

## 缓存穿透、击穿、雪崩

**穿透**：查询不存在的数据，请求每次都打到数据库。
- 方案：缓存空值（短 TTL）、布隆过滤器前置拦截、参数校验。

**击穿**：某个热点 key 过期瞬间，大量并发请求同时打到数据库。
- 方案：互斥锁（只让一个线程回源，其它等待）、逻辑过期（不设 TTL，异步更新）、热点 key 永不过期。

**雪崩**：大量 key 同时过期，或 Redis 宕机，流量全部压到数据库。
- 方案：过期时间加随机值打散、多级缓存（本地 Caffeine + Redis）、熔断降级、Redis 高可用（哨兵/集群）。

## Redis 持久化：RDB 与 AOF

**RDB**：定时生成内存快照。
- 优点：文件紧凑、恢复快，适合备份与全量恢复。
- 缺点：两次快照之间的数据会丢失；fork 子进程时若内存大会有明显停顿。

**AOF**：追加写命令日志。
- 优点：数据更安全，`appendfsync everysec` 最多丢 1 秒数据。
- 缺点：文件大、恢复慢。

**混合持久化**（Redis 4.0+）：AOF 重写时前半部分写 RDB 格式快照，后半部分追加增量命令，兼顾恢复速度与数据安全，是生产推荐配置。

## 分布式锁的实现与坑

基本实现：`SET lock_key unique_value NX PX 30000`。

三个关键点：
1. **必须设过期时间**，否则宕机后锁永不释放。
2. **value 必须是唯一标识**（如 UUID），释放时用 Lua 脚本先比对再删除，避免误删别人的锁。
3. **看门狗续期**：业务执行时间可能超过锁的过期时间，需要后台线程定期续期（Redisson 的 watchdog 默认每 10 秒续到 30 秒）。

**单点问题**：主从架构下主节点宕机、锁尚未同步到从节点时，会出现两个客户端同时持锁。RedLock 试图解决但争议较大，生产更推荐用 ZooKeeper 或 etcd 的租约机制。

## Redis 主从复制与哨兵

**主从复制**：从节点执行 `REPLICAOF` 后与主节点建立连接，主节点通过 RDB 全量同步 + 命令传播增量同步。复制是异步的，因此存在数据丢失窗口。

**哨兵（Sentinel）**：监控主从节点，主节点故障时自动选举新主并通知客户端。判定下线分主观下线（单个哨兵认为不可达）与客观下线（超过 quorum 个哨兵认同）。

**Cluster**：数据分片，16384 个哈希槽分布在多个主节点上，每个主节点带从节点。支持水平扩容，但多 key 操作要求 key 在同一槽（可用 hash tag `{}` 强制）。
