# D9 提示词 A-B-C 对照记录

> 复现命令：`mvn spring-boot:run -Dspring-boot.run.profiles=prompt-ab`
> 代码：`smoke/PromptAbRunner.java`（驱动）+ `agent/InterviewerPrompts.java`（三版提示词）
> 记录时间：2026-10-30

---

## 一、实验设计：单变量控制

提示词对照最容易犯的错是"一次改三处，然后说新版更好"——那样根本无法归因。这里把**除 instruction 以外的一切**都锁死：

| 控制项 | 取值 | 如何保证 |
|---|---|---|
| 题目 | 同一道 `HashMap 的扩容机制是怎样的？为什么负载因子默认是 0.75？` | 同一个 `QuestionMapper` 查询结果 |
| 候选人回答 | 同一段话 | 常量 `CANDIDATE_ANSWER` |
| 模型 | `deepseek-chat` | 同一个 `LangChain4j` Bean |
| temperature | 0.7 | `DeepSeekModelConfig` 固定 |
| 工具 | `pick_question` | 三版都注册同一个 `FunctionTool` |
| 会话 | 每版独立 user + 独立 session | 避免上下文互相污染 |
| 轮次 | 每版跑两轮：开场出题 → 提交回答 | 同一个 `Runner` |

**唯一变量**：`instruction`（v1 / v2 / v3）。

## 二、三版提示词的递进差异

三版不是"三个风格"，而是**逐条叠加**，每条改动都能对上后面的输出差异：

| 维度 | v1 基线 | v2 加规则 | v3 加语气与格式 |
|---|---|---|---|
| 角色 | 一句"你是 Java 后端面试官" | 加平台名与职责 | 加人格「陈老师」+ 8 年经验 + 风格约束 |
| 输出结构 | 无 | "先一句话点评，再提出问题" | **固定两段标签**：`评价：` / `追问：` |
| 追问锚点 | 无要求 | 必须锚定回答中**具体的点**，并给了示例 | 按回答类型分 5 条策略（名词→原理/边界、结论→为什么/反例、完整→工程场景、答错→指出错误、连续答不出→提示再换题） |
| 长度 | 无 | ≤120 字 | ≤150 字 |
| 语气 | 无 | 无 | 禁鼓励词、禁感叹号、禁 emoji；要求事实性评价 |
| 禁止项 | 无 | 不编造、不透露 AI | 不透露参考答案原文、不编造候选人经历 |

## 三、实际输出（逐字记录）

### V1（两轮合计 3634 ms）

```
[出题] 提问：HashMap 的扩容机制是怎样的？为什么负载因子默认是 0.75？

[追问] 提问：你提到扩容后要"重新放一遍"，那 JDK8 里扩容时元素的新位置具体是怎么计算的？需要重新计算 hash 吗？
```

### V2（两轮合计 2702 ms）

```
[出题] 提问：HashMap 的扩容机制是怎样的？为什么负载因子默认是 0.75？

[追问] 回答方向对，但太笼统。追问：JDK8 扩容后元素重新分配时，需要重新计算 hash 吗？如果不需要，那新下标是怎么确定的？
```

### V3（两轮合计 2468 ms）

```
[出题] 提问：HashMap 的扩容机制是怎样的？为什么负载因子默认是 0.75？

[追问] 评价：翻倍和重放这个方向对，但漏了触发条件（阈值=容量×0.75）和 JDK8 重哈希的细节，负载因子为什么 0.75 也没答。

追问：你说"重新放一遍"，JDK8 扩容时每个元素的新下标是怎么算出来的，需要重新计算 hash 吗？
```

## 四、差异归因

| 观察到的差异 | 对应到哪条改动 |
|---|---|
| v1 **完全没有评价**，直接抛下一问 | v1 没有"先点评再提问"这条规则，模型默认只完成"提下一个问题" |
| v2 有一句点评，但只到"太笼统"这种程度 | v2 有"先一句话点评"，但没有规定**点评什么**，所以模型给了笼统判断 |
| v3 的评价**点名了三个缺失点**（触发条件、JDK8 重哈希、0.75 的原因） | v3 把点评定义成"指出回答中准确与缺失的点"，且人格设定"严格、只问关键点"把输出往具体方向压 |
| v2 / v3 都锚定了"重新放一遍"，v1 也锚定了 | 锚点能力不是 v2/v3 的专利——v1 也能从上下文里抓到关键词。**"锚定具体名词"这条规则的边际收益比预期小** |
| v3 用了标签 `评价：` / `追问：`，前端可直接解析 | v3 的"固定三段格式"（实际输出两段，出题轮单独约束成一行） |
| v3 无感叹号、无鼓励词 | "语气约束"三连生效 |

**最有价值的一条**：v2 的规则是"先一句话点评"，输出就停在"方向对，但太笼统"；v3 把点评改成"指出准确与缺失的点"，输出立刻变成可核查的三点清单。**规则写得越可判定，模型输出越可评估**——这比"写得更有礼貌"重要得多。

## 五、结论与后续动作

1. **默认版本定为 v3**（`InterviewProperties.promptVersion` 已是 `v3`，`InterviewerPrompts.of()` 未知版本回落 v3）。
2. **v3 的两段标签直接服务前端**：`评价：` / `追问：` 是稳定分隔符，D13（SSE）/ D25（chat UI）做对话界面时可以按行切分渲染（评价灰字、追问黑字）。（D11 归档勘误：原文写的是 D12，与计划不符）
3. **v2 的"锚定具体点"规则保留在 v3 里**，但它的实际贡献低于预期，不作为卖点写进简历。
4. **v1 保留为基线**，不做删除——它是"没有规则时模型会怎样"的证据，D9 复盘里要用。

## 六、诚实声明（局限）

- **样本量 = 1**。每版只跑了一次，temperature=0.7，输出有随机性。本文记录的是"这一次的可观察差异"，**不是统计结论**。
- **耗时数据不可用于性能对比**：三版耗时 3634 / 2702 / 2468 ms 是两轮合计，且首轮含 JVM 预热、连接建立、模型端排队等噪声，v3 反而最快不能说明"提示词更长更快"。
- **只测了一道题、一段回答**。换题型（如开放设计题、连续答错场景）结论可能不同。
- 若要形成可引用的结论，应扩到 **≥10 题 × 3 版 × 3 次重复**，并用固定 seed 或 temperature=0 降低方差——这是 D9 之后的可选增强项，不阻塞主线。
